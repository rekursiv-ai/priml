# openai/math

This baseline trains a policy to prove Lean 4 theorems from
[openai/math][openai-math]. FineEnvs publishes 369 challenges as Harbor tasks.
Each task runs in a sandbox with no network access. The agent edits
`/workspace/Submission.lean`, submits a proof, and gets reward 1 if a separate
verifier accepts it, or 0 otherwise.

The task instructions, challenges, grader, and container image come from the
FineEnvs dataset at the revision pinned by PriML. PriML adds the agent, rollout
runtime, and training loop.

Training uses lemma tasks rather than the 369 full challenges. A challenge
reference proof spans 67 library modules at the median, so a 4B policy would
almost always receive reward 0. `scripts/lemma_tasks.py` cuts the same Lean
library into smaller tasks, using the dataset's unchanged grader. See
[Lemma tasks](#lemma-tasks).

## Experiments

| Experiment | Purpose |
|---|---|
| `exp000` | Qwen3.5-4B, 500 updates, and live rollouts on lemma tasks |
| `exp_smoke` | One small CPU update from a saved fixture |

`exp000` is the frozen root experiment. Later experiments should change one
thing at a time. It trains on 8 lemma tasks per update, with 32 attempts per
task: 256 episodes per update for 500 updates. Its hypothesis and measurement
plan are in its docstring. It has no results yet.

One update works as follows:

1. Harbor starts 32 attempts for each of 8 tasks in Daytona sandboxes.
2. The agent runs one Lean episode per sandbox against the policy server.
3. Harbor and the dataset verifier grade each attempt.
4. PriML reads the verdicts and token transcripts from disk.
5. PriML packs the batch and performs one DPPO update.
6. PriML exports the policy and restarts the rollout server with the new weights.

The learner saves a checkpoint every 10 updates, keeps the latest three, and
keeps every 50th. On restart, it replays complete rollout batches that were
saved but not yet trained.

Groups whose rewards are all equal are dropped because their centered advantage
is zero, then refilled from the next task draw. If the runner cannot form an
update after 64 draws
(`runner.max_draws_per_update`), it fails instead of spending sandboxes
indefinitely.

The run has no configured seed. Task order starts from OS entropy, and the
seed is saved with the task cursor in every committed rollout batch. Resuming
therefore continues the same order. The fixed-corpus tool also commits each
update with its cursor and refuses older unmarked shards.

Every graded attempt gets a line in `openaimath_attempts.jsonl`, including its
step, slot, draw, task, Harbor job and trial, group outcome
(`kept`, `zero_spread`, or `unusable`), reward, grader reason, finish reason,
turns, token counts, sandbox and grading times, timestamps, and submitted-file
digest. Summing the recorded times gives the Lean cost of the run. The learner
only trains on kept rollout groups.

Each draw has its own job directory:
`jobs/openaimath_step_S_slot_P_draw_D_try_T`. Dropped trials remain on disk,
and interrupted updates use a `_retry_N` suffix rather than replacing trials
already named in the attempt log. Each transcript,
`agent/openaimath_episode.jsonl`, records the final graded files,
`submission_files`, `submission_sha256`, and episode start and end times.
Job directories are never deleted, so disk use grows with every draw.

`exp_smoke` checks the local data, model, loss, and optimizer path. Its two
saved responses have different rewards, so the update has a nonzero gradient.
Their log probabilities came from the seeded smoke model, giving an initial
importance ratio of exactly 1. It needs no checkpoint, snapshot, or live
runtime:

```bash
uv --quiet run --frozen python -m priml priml.baselines.openaimath.experiments.exp_smoke
```

The response tokens were not generated by that model, so this is not an
on-policy result or benchmark score.

## Lemma tasks

OpenAI Math's Lean library (`lean/OAI`) is also a corpus of ordinary lemmas.
Each lemma has a statement, the file context before it, and a proof accepted by
the kernel. `scripts/lemma_tasks.py` turns a lemma into a task:

- The challenge is the module up to the lemma, with that proof replaced by
  `sorry`; earlier declarations keep their proofs.
- The reference solution is the module through the end of the lemma proof.
- `environment/`, `tests/grade.py`, and `tests/test.sh` are copied byte for
  byte from a published task.

The image contains Mathlib but not the OAI library. The cutter keeps only
modules that import Lean or Mathlib, and only public `theorem` and `lemma`
declarations. It skips modules over 24 KB or containing `sorry`, `admit`,
`native_decide`, `axiom`, `unsafe`, or `extern`.

The split is by challenge family because all challenges share one library:

- A salted hash holds out the bottom 52 of 256 values, about 20% of families.
- Test-side modules include every OAI module imported directly or indirectly
  by a held-out challenge proof.
- Training lemmas come from modules used by training challenges and by no
  held-out or unpublished challenge.

At the pinned source this produces 173 training families and 41 held-out
families, with 20,652 training lemmas and 5,341 held-out lemmas. No module is
on both sides. It also produces 72 held-out published challenges in
`lemmas/official_test_tasks.txt`.

The two evaluation sets serve different purposes:

- **Progress:** pass@1 on a fixed seeded sample of 256 held-out lemma tasks.
- **Protected score:** pass@k on the 72 held-out published challenges, run only
  at the start and end of a campaign, never to select a fork.

The dataset validated its 369 tasks with its own oracle. The lemma tasks were
cut by this baseline and have not been graded yet, so an `--oracle` run on a
sample checks that the cut tasks build and grade correctly.

## Prepare assets

From the PriML repository:

```bash
uv --quiet run --frozen python -m priml.baselines.openaimath.scripts.prepare_data
```

This stages:

- `FineEnvs/openai-math` at revision `d7056fd` into
  `/opt/scratch/datasets/openaimath/openai-math` (369 tasks, generator, and
  registry).
- A sparse `openai/math` checkout at `adc7f12`, containing `lean/OAI` and
  `lean/ComparatorChallenges`, in
  `/opt/scratch/datasets/openaimath/openai-math-source` (about 2.1 GB).
- Lemma tasks in the dataset's `lemmas/` directory: `train/`, `test/`,
  `split.json`, and `official_test_tasks.txt` (about 364,000 files and 1.3 GB).
- `hamishivi/Qwen3.5-4B` at the PriML-pinned revision, shared with the learner.

Preparation checks the dataset oracle results, source commit, task count, and
registry. It records every staged-file digest and the included lemma tasks in a
manifest. Later runs reject changed, missing, or extra files. It also completes
interrupted checkpoint downloads. The split marker is written last; an
interrupted first run must restart in a clean dataset directory.

Building the Daytona snapshot needs Docker and a Daytona API key. Preparation
prints this command instead of running it:

```bash
cd /opt/scratch/datasets/openaimath/openai-math/generator
uv --quiet run --frozen --no-project --with daytona-sdk \
  python -m openai_math_harbor.snapshot
```

The expected snapshot is `openai-math-lean-62f5d72497ea`. It is derived from
the generator's `image/` digest, takes about an hour, and uses about 9 GB.
Harbor's ten-minute auto-snapshot timeout is too short for Mathlib.

## Run `exp000`

`exp000` needs one 8-GPU node, the staged checkpoint, the Daytona snapshot, and
a Daytona API key. Four learner processes use GPUs 0-3. Four single-GPU vLLM
engines use GPUs 4-7 through `runner.rollout_gpus` and
`runner.data_parallel_size`. The live dataset rejects overlapping devices.

Harbor 0.24 must be installed in the learner environment. vLLM is launched
separately as `uvx vllm==0.19.1`.

```bash
export DAYTONA_API_KEY=<daytona-api-key>
uv --quiet run --frozen --with harbor==0.24.0 \
  python -m torch.distributed.run --nproc_per_node=4 \
  -m priml priml.baselines.openaimath.experiments.exp000
```

Rank zero starts one Harbor job per prompt with `-k 32` over `lemmas/train`.
The eight prompt jobs run concurrently, so the Daytona account must allow 256
sandboxes. Verdicts come from `verifier/reward.txt`; transcripts come from the
agent log directory.

Before the first episode, the agent uploads the task's
`tests/Challenge.lean` to the submission path. Published tasks already have
that file in the image. Lemma tasks have it only in their task directory, so
the agent uses Harbor's `task_dir`.

The agent uses the checkpoint tokenizer's chat template and stops on its
end-of-turn token, `<|im_end|>` for Qwen3.5. It reads directives only after
`</think>`, so reasoning about `SUBMIT` does not submit the proof. Every
appended token counts toward the 65,536-token response budget.

The learner exports a Hugging Face checkpoint, stops vLLM, and starts a new
server on the exported weights. The agent reaches the policy over HTTP from
outside the sandbox, so this makes the served policy exactly the checkpoint
artifact. The cost is one server restart per update.

The final checkpoint is written to
`/opt/scratch/runs/openaimath/exp000/export`.

## Evaluate

Serve a policy, then run the evaluator. The progress metric is pass@1 on the
fixed 256-task held-out lemma sample:

```bash
uv --quiet run --frozen --with harbor==0.24.0 \
  python -m priml.baselines.openaimath.scripts.eval \
  --base-url http://127.0.0.1:8000 \
  --limit 256
```

The protected score is pass@8 on the held-out published challenges:

```bash
uv --quiet run --frozen --with harbor==0.24.0 \
  python -m priml.baselines.openaimath.scripts.eval \
  --base-url http://127.0.0.1:8000 \
  --attempts 8 \
  --tasks-dir /datasets/openaimath/openai-math/tasks \
  --task-list /datasets/openaimath/openai-math/lemmas/official_test_tasks.txt
```

By default, `prepare_data.py` supplies the task directory, snapshot, and
tokenizer under `--base-dir` (`/opt/scratch`). `--limit` takes a seeded subset
in the runner's draw order, so the 256-task sample is stable. Use
`--task-names` or `--task-list` for an explicit list. Results go to
`/opt/scratch/runs/openaimath/eval/eval_report.json` unless `--report` is set.
The report includes pass@1, unbiased pass@k, mean reward, and attempts that
never reached the grader.

`--oracle` uses Harbor's reference-solution agent instead of this policy. It is
the positive control for a new machine:

```bash
# The dataset's own tasks: every task must be accepted.
uv --quiet run --frozen --with harbor==0.24.0 \
  python -m priml.baselines.openaimath.scripts.eval --oracle \
  --tasks-dir /datasets/openaimath/openai-math/tasks --limit 4

# A sample of lemma tasks: checks the cut.
uv --quiet run --frozen --with harbor==0.24.0 \
  python -m priml.baselines.openaimath.scripts.eval --oracle --limit 64
```

The oracle does not exercise this baseline's agent. A policy run on one or two
tasks does.

## Validation

The CPU tests cover the episode protocol, chat framing, budgets, sampler,
transcript conversion, task draws, seed persistence, group filtering, draw
caps, concurrency, job naming, GPU placement, live restarts, commits, resume
replay, the other-rank path, lemma cutting and splitting, asset manifests,
source and lemma checks, and pass@k. They fake Harbor, vLLM, and the sandbox,
so they need no GPU, Daytona account, or network.

```bash
uv --quiet run --frozen pytest priml/baselines/openaimath
```

The Harbor agent test skips when Harbor is not installed. `exp_smoke` has run
end to end on CPU with `ratio_mean=1.0` and a nonzero gradient. The CI
`compute_training` test also checks that the update moves weights.

No real Daytona training or grading run has been completed, so there are no
`exp000` results, pass@k numbers, or comparisons with published openai/math
results yet. The lemma counts came from the pinned source, but no Lean
toolchain has compiled a lemma task. An oracle run is the first real check.
The source checkout matched a full clone file for file. Chat framing was
checked against the Qwen3.5-4B tokenizer, but token reporting and stop-token
behavior under vLLM 0.19.1 were checked only with fakes. The first real
episode confirms those behaviors.

## Bit-for-bit reference

OpenAI Math publishes a grader, not a training recipe, so there is no numerical
training result to reproduce. The bit-for-bit contract is the reward: a proof
is accepted only when the unchanged dataset verifier accepts it.

Three checks protect that contract:

1. Harbor runs the dataset's published container and grader.
2. `prepare_data.py` derives the image name from the generator and rejects
   unaccepted oracle results or a different source commit.
3. `--oracle` must accept every sampled reference solution before policy
   evaluation begins.

Lemma tasks use the same image and grader, but their reference proofs are cut
by this baseline. The oracle therefore also validates the cutter.

The numerical side uses TMax's DPPO train step unchanged; its bit-for-bit
golden lives in `baselines/tmax`. The smoke log probabilities are regenerated
with the same seeded smoke model used by the training step, so its initial
`ratio_mean=1.0` and weight update are reproducible.

baseline supplies the task and rollout substrate around the DPPO learner.
