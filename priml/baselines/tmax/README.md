# TMax

Train a terminal agent based on the released TMax recipe. TMax generates and
checks terminal rollouts with Ray, vLLM, and its sandbox tools. PriML trains
the Qwen3.5 policy with DPPO and sends each updated policy back to vLLM.

This baseline follows the [TMax paper][tmax-paper] and
[TMax source at `6d3d606`][tmax-source]. [DPPO paper][dppo-paper] describes
the training objective.

## Experiments

| Experiment | Purpose |
|---|---|
| `exp000` | Qwen3.5-4B, 500 learner updates, and live TMax rollouts |
| `exp_smoke` | One small CPU update from a saved fixture |

`exp000` is the baseline for later experiments. It uses 8 prompts with 32
samples each, or 256 accepted rollouts per update. Its budget of 128,000
accepted rollouts gives 500 updates. TMax may generate more rollouts because
it replaces prompt groups whose rewards are all the same.

1. TMax supplies one accepted batch of terminal rollouts.
2. PriML packs the batch and performs one DPPO update.
3. PriML sends the updated weights to vLLM before requesting the next batch.

TMax generates rollouts asynchronously and keeps up to four updates' prompts
in flight. Some rollouts in a later batch may have started under older weights.
TMax drops results that are too old.

The learner saves a checkpoint every 10 updates, keeps the latest three, and
keeps every 50th checkpoint. On restart, it replays complete rollout batches
that were saved but not yet trained. Incomplete and in-flight work may be
collected again.

`exp_smoke` checks the local data, model, loss, and optimizer path. Its two
saved response slices have different rewards, so the update has a nonzero
gradient. Their log probabilities were computed by the seeded smoke model,
which gives an initial mean importance ratio near 1. The responses were not
generated by that model, so this is not an on-policy result or a benchmark
score.

It needs no staged checkpoint or live TMax runtime:

```bash
uv --quiet run --frozen python -m priml priml.baselines.tmax.experiments.exp_smoke
```

## Prepare assets

From the PriML repository:

```bash
uv --quiet run --frozen python -m priml.baselines.tmax.scripts.prepare_data
```

This stages:

- `hamishivi/Qwen3.5-4B` at a revision pinned by PriML;
- `allenai/tmax-15k-open-instruct` parquet and terminal tasks at a revision
  pinned by PriML;
- TMax source at commit `6d3d606`; and
- one published 9B rollout shard for parity and debugging.

The released 4B launcher names the model and dataset but does not pin their
revisions. PriML pins them so later runs can use the same inputs.

The preparation manifest records source revisions and file digests. Later
preparation runs reject changed, missing, or extra staged files. `exp000` does
not train on the published 9B shard. It writes fresh 4B rollouts under
`/opt/scratch/runs/tmax/exp000/rollouts`.

## Run exp000

The released 4B launcher requests four 8-GPU nodes: two for 16 learner
processes and two for 16 one-GPU vLLM engines. This is not a laptop
experiment.

The learner imports both PriML and TMax's rollout code. Use Python 3.12 and
the pinned TMax environment, then install PriML into it:

```bash
TMAX=/opt/scratch/datasets/tmax/upstream/tmax
cd "$TMAX/training/open-instruct"
uv sync --frozen
uv pip install --python .venv --no-deps -e /path/to/priml
uv pip install --python .venv \
  configgle einshape jaxtyping typeguard rustbpe torchao==0.17.0 \
  lpips imageio-ffmpeg imagesize opencv-contrib-python-headless \
  pygame-ce pyturbojpeg webp
uv --quiet run --frozen python -c \
  "import priml.baselines.tmax.experiments, open_instruct.grpo_fast, ray, vllm"
```

The TMax lock uses torch 2.10.0. PriML normally pins torch 2.11.0, so PriML CI
does not test this combined environment.

For this PriML run, start Ray on the inference nodes only. On Beaker, the pinned
`configs/beaker_configs/ray_node_setup.sh` starts the head on replica 0 and
joins each other replica. Unlike the upstream launcher, which also puts
trainers on Ray, PriML uses `torch.distributed` for the learner nodes. Do not
add their GPUs to Ray.

Point both learner nodes at the Ray head, then launch one process per training
GPU:

```bash
export RAY_ADDRESS=<inference-head>:8888
export TRAIN_RDZV_ENDPOINT=<training-head>:29400
export TRAIN_RDZV_ID=tmax-exp000
export NODE_RANK=<0-or-1>
TMAX=/opt/scratch/datasets/tmax/upstream/tmax
uv --quiet run --frozen --project "$TMAX/training/open-instruct" \
  python -m torch.distributed.run \
  --nnodes=2 --nproc_per_node=8 --node_rank="$NODE_RANK" \
  --rdzv_backend=c10d --rdzv_endpoint="$TRAIN_RDZV_ENDPOINT" \
  --rdzv_id="$TRAIN_RDZV_ID" \
  -m priml priml.baselines.tmax.experiments.exp000
```

Run this command on both learner nodes with `NODE_RANK` set to `0` and `1`.
The final Hugging Face checkpoint is written to
`/opt/scratch/runs/tmax/exp000/export`.

PriML replaces upstream DeepSpeed ZeRO-3 and sequence parallelism with FSDP.
It follows the rollout settings and global DPPO loss, but the two distributed
systems have not been shown to produce identical full-scale arithmetic. The
paper selected its best checkpoint using Terminal-Bench Lite every 100 updates.
`exp000` exports the final checkpoint instead; it does not select the best one.

## Evaluate

Prepare the pinned TMax environment. The evaluator loads Daytona SDK
`0.165.0` alongside TMax's locked Harbor `0.6.6` for the Harbor run; it
does not change TMax's project or lockfile. TMax has no `daytona` project
extra.

```bash
TMAX=/opt/scratch/datasets/tmax/upstream/tmax
cd "$TMAX"
uv sync --frozen
uv --quiet run --frozen --no-sync --with daytona==0.165.0 \
  python -c "import daytona"
export DAYTONA_API_KEY=<daytona-api-key>
```

Run one Terminal-Bench job:

```bash
TMAX=/opt/scratch/datasets/tmax/upstream/tmax
uv --quiet run --frozen --project "$TMAX/training/open-instruct" \
  python -m priml.baselines.tmax.scripts.eval \
  /export \
  --results-dir /eval \
  --job-name exp000-terminal-bench
```

The evaluator starts vLLM, runs Harbor with TMax's Vanillux agent, copies the
trial results, and runs TMax's `compute_stats.py`. The defaults use
`terminal-bench@2.0`, Daytona, five attempts, concurrency 16, vLLM `0.19.1`,
and the `qwen3_xml` tool parser.

Each job records the checkpoint file hashes and evaluation settings. Reusing a
job name with different recorded inputs is rejected.

This command runs one job using settings from TMax's manual evaluation example.
The paper used Terminal-Bench Lite and 2.1 during development, then ran
Terminal-Bench 2.0 with Daytona several times for its final results. One job
with five attempts does not reproduce that evaluation campaign.

## Validation

The CPU tests compare PriML with the pinned TMax source for:

- packed rollout rows and centered advantages;
- current-policy log probabilities, DPPO divergence, mask, and loss;
- Qwen3.5 logits and gradients; and
- five sequential optimizer updates and final weights.

These tests use tiny float32 models. They do not cover live Ray placement,
vLLM weight transfer over NCCL, bf16 FSDP training, or full 67,584-token
sequences. No `exp000` training or evaluation score has been recorded.

Run the TMax test suite:

```bash
uv --quiet run --frozen pytest priml/baselines/tmax
```

The separate Hugging Face model parity test needs the optional `hub`
dependencies:

```bash
uv --quiet run --frozen --extra hub pytest priml/model/transformer/qwen3_5_hf_test.py
```
